Лекц 3-ын 6 хэсэгтэй форматаар бичсэн. Тоонууд дээрх baseline-аас гарсан.

## SLO

| Сценарио | SLI | Босго | Цонх |
|---|---|---|---|
| Performance | /cart/add latency | p95 < 10 ms, p99 < 20 ms | 20 VU, 1 мин |
| Reliability | /pay error rate | < 7.5% | 20 VU, 1 мин |
| Availability | бүх хүсэлтийн амжилт (checks) | >= 90% | 20 VU, 2 мин, 10 с зогсолттой |
| Нэмэлт | /report latency | p95 < 420 ms | 20 VU, 1 мин |

Яагаад эдгээр тоо:
- Cart: baseline p95 2.09 ms, p99 4.04 ms. localhost дээр 1-2 ms-ийн утга бага зэрэг хэлбэлзэхэд л хэд дахин өөрчлөгддөг тул ~5 дахин нөөц авч 10/20 ms болгосон.
- Pay: сервер 5% алдаа гаргадаг, 1 минутад ~930 төлбөрт энэ хувь 0.7% орчим хэлбэлздэг тул 7.5% гэвэл санамсаргүй унахгүй ч алдаа нэмэгдвэл барина.
- Availability: 2 минутын 10% = 12 с. 10 секундийн зогсоох туршилт багтах ёстой гэж 90% сонгосон.
- Report: 200-400 ms санамсаргүй хүлээдэг тул p95 нь онолоороо 390 ms (baseline 388.77 ms), 30 ms нөөц нэмж 420 ms.

Error budget (цагаар): 2 мин * (1 - 0.90) = 12 секунд зогсох эрхтэй.

## PASS

[slo-test.js](slo-test.js) дотор endpoint бүрийг name tag-аар ялгаж threshold тавьсан. Босгууд дээрх SLO хүснэгттэй ижил.

```bash
k6 run --no-color slo-test.js > results/pass.txt 2>&1
```

Гаралт: [results/pass.txt](results/pass.txt), exit code 0.

| Threshold | Үр дүн |
|---|---|
| cart p(95)<10 | 1.87 ms PASS |
| cart p(99)<20 | 3.63 ms PASS |
| pay rate<0.075 | 5.69% PASS |
| checks rate>=0.90 | 98.10% PASS |
| report p(95)<420 | 390.57 ms PASS |

`server_responded` бол threshold биш, сервер хариу өгсөн эсэхийг (500 ч хамаагүй) тоолох гэж нэмсэн metric. Chaos дээр ашигласан.

## Chaos туршилт

2 минутын тест явж байхад серверийг зогсоож, 10 секундийн дараа дахин асаасан. Гараар Ctrl+C дараад цаг хэмжихэд яг гарахгүй байсан тул [chaos.sh](chaos.sh) бичсэн. 40 дахь секундэд SIGINT (Ctrl+C-тэй ижил) илгээгээд, 10 с хүлээж `node server.js` асаана.

```bash
bash chaos.sh
```

Гаралт: [results/chaos.txt](results/chaos.txt), [results/chaos-timeline.txt](results/chaos-timeline.txt)

- 16:05:40.615-д зогсоосон, 16:05:50.989-д эхний 200 ирсэн. Сэргэх хугацаа 10.374 с, сценариогийн <= 12 с хангагдсан. Сервер өөрөө асахад 0.258 с зарцуулсан, үлдсэн нь миний хүлээсэн 10 секунд.
- k6 лог дээр 611 удаа `connection refused` гарсан.

| Threshold | Chaos үед |
|---|---|
| checks rate>=0.90 | 87.77% FAIL |
| pay rate<0.075 | 15.22% FAIL |
| cart p(95)<10 / p(99)<20 | 1.82 / 5.27 ms PASS |
| report p(95)<420 | 388.76 ms PASS |

exit code 99, availability ба reliability хоёулаа унасан.

**Availability-г хүсэлтээр тооцвол:** 4998 / 5694 = 87.77%. Budget нь 5694 * 10% = 569 хүсэлт байхад 696 check унасан тул хэтэрсэн. Гэтэл цагаар бол 10.374 с зогссон нь 12 с-ийн budget-д багтана (120 с-ээс 10.374 с хасвал 91.35%).

Хоёр тоо яагаад зөрж байгаа вэ гэвэл:
1. Сервер унасан үед хүсэлт шууд connection refused авч буцдаг, /report-ын 200-400 ms хүлээлт алга болдог. Тиймээс VU-ууд илүү хурдан давтаж, 10.374 секундэд 611 хүсэлт буюу секундэд ~59 хүсэлт унасан. Хэвийн үед 45.55 хүсэлт/с (pass.txt). Pass үед хамгийн богино давталт 1.2s байсан бол chaos үед 1s болсон нь үүнийг харуулж байна.
2. checks нь /pay-ийн санаатай 500-г ч унасан гэж тоолдог. Cart 203, report 204 удаа унасан тул pay-ийн зогсолтын алдаа 611 - 203 - 204 = 204, үлдсэн 289 - 204 = 85 нь санаатай 500.

Тэгэхээр 12 секундийн budget хүсэлтээр бодоход (569 - 85) / 59 буюу 8 орчим секунд л болж байна. Миний бодлоор SLO хэт өөдрөг байсан биш, цагаар бодоод хүсэлтээр хэмжсэн нь зөрсөн. Бас зогсолтын ихэнх нь миний хүлээсэн хугацаа байсан, pm2 шиг автоматаар дахин асаадаг зүйл байсан бол ингэж удаан зогсохгүй.

**Reliability яагаад бас унав:** /pay-ийн 289 алдааны 204 нь сервер байхгүй үед илгээсэн хүсэлт. Нэг эвдрэл хоёр SLO-г зэрэг зөрчиж байна. Availability-г "сервер ямар нэг хариу өгсөн эсэх" (status != 0), reliability-г "хариу өгсөн /pay-ийн дундах 5xx хувь" гэж салгавал зогсолт зөвхөн availability-д, 500 зөвхөн reliability-д нөлөөлнө. server_responded chaos үед 89.26% (5083/5694) гарсан, салгаж тооцсон pay-ийн алдаа 85 / 1694 = 5.01% болж 7.5%-аас бага.

## FAIL

[slo-test-fail.js](slo-test-fail.js) нь slo-test.js-тэй ижил, зөвхөн /report-ын босгыг `p(95)<100` болгосон. /report 200 ms-ээс хурдан хариулдаггүй тул заавал унана.

Гаралт: [results/fail.txt](results/fail.txt)

```
✗ 'p(95)<100' p(95)=390.04ms
level=error msg="thresholds on metrics 'http_req_duration{name:report}' have been crossed"
```

Энэ хоёр мөр FAIL-ийг харуулж байна. Бусад threshold PASS хэвээр (checks 98.45%, cart p95 1.6ms, pay 4.62%).

Exit code: k6 **99** буцаасан. Нэг зүйл анзаарсан: зааврын `k6 run slo-test-fail.js 2>&1 | tee results/fail.txt; echo "exit=$?"` командаар ажиллуулахад `exit=0` гарсан. Pipe-ийн дараа `$?` нь tee-ийн exit code байдаг юм байна. `${PIPESTATUS[0]}`-ээр харахад 99 ([results/fail-exitcode.txt](results/fail-exitcode.txt)). CI дээр pipefail тавихгүй бол унасан тест ногоон харагдах эрсдэлтэй.

/cart/add-ыг p(95)<50 болговол localhost дээр PASS хэвээр байна, учир нь cart 2 ms орчим хариулдаг, 50 ms хэт сул.

Энэ ажиллуулалтад cart p99 15.67 ms гарсан, бусад удаа 3.63-5.27 ms байсан. localhost дээр p99 их хэлбэлздэг тул 1.5 дахин биш 5 дахин нөөц авсан нь зөв байж.

## Дүгнэлт

Сценариог SLO, дараа нь threshold болгоход хамгийн хэцүү нь босгын тоог сонгох байсан. Эхлээд baseline хэмжээгүй бол зааврын p(95)<200-г хуулах байсан, гэтэл cart ердөө 2.09 ms-д хариулдаг. Босго бүрд өөр үндэслэл хэрэгтэй болсон: cart-д localhost-ийн хэлбэлзэл, pay-д санаатай 5% алдааны хэлбэлзэл, report-д 200-400 ms-ийн тархалт. Fail ажиллуулалтад cart p99 15.67 ms гарсан нь 5 дахин нөөц авсан маань зөв байсныг харуулсан. Chaos туршилт сэргэх хугацааны хэмжүүрийг баталсан, 10.374 с нь 12 с-ээс бага. Харин availability 87.77% гарч 90%-ийн SLO-г зөрчсөн тул энэ хэмжүүрийг үгүйсгэсэн. Шалтгаан нь би budget-ээ цагаар бодсон атал checks хүсэлтээр тоолдог, сервер унасан үед хүсэлт хурдан унадаг тул нэг секунд илүү олон хүсэлт иддэг. Мөн нэг зогсолт reliability SLO-г хамт унагасан нь SLI-уудыг тусад нь тодорхойлох хэрэгтэйг харуулсан. 10 секундийн зогсолтын ихэнх нь миний хүлээлт байсан тул бодит системд автоматаар дахин асаах нь хамгийн их тус болно. Бас `| tee` ашиглахад k6-ийн exit code алдагддагийг олж мэдсэн нь CI дээр хэрэгтэй санагдсан.

## AI өнцөг (нэмэлт)

Claude-д зөвхөн server.js-ийн кодыг өгөөд "6 хэсэгтэй форматаар 3 чанарын сценарио бич" гэж шинэ чат дээр асуусан. Хариуг засахгүйгээр [ai/ai-scenarios.md](ai/ai-scenarios.md)-д хуулсан.

| | AI | Миний хэмжилт | Миний SLO |
|---|---|---|---|
| cart p95 | <= 50 ms | 1.6-2.09 ms | < 10 ms |
| report p95 | <= 450 ms | 388.76-390.57 ms | < 420 ms |
| pay | амжилт >= 99.5% (30 хоног) | алдаа 4.62-5.91% | < 7.5% |
| availability | байхгүй | 87.77% (chaos) | >= 90% |

AI-ийн /report-ын 450 ms кодоос зөв бодогдсон бөгөөд миний хэмжилттэй таарч байна, харин cart-ийн 50 ms бодит 2 ms-ээс 25 дахин сул тул юу ч барихгүй. Хамгийн том дутуу нь availability сценарио огт бичээгүй, сервер унах өдөөлтийг мартсан. /pay дээр retry, idempotency key, alert гэж бичсэн ч server.js-д эдгээр байхгүй, өөрөөр хэлбэл байхгүй зүйл зохиосон. Мөн өдөөлтийг "хэрэглэгч төлөх" биш "gateway алдаа гаргах" болгосон, лекцийн форматын оронд Эх үүсвэр, Артефакт гэсэн өөр 6 хэсгийг ашигласан. Гэхдээ төлбөрт 99.5% амжилт, давхар төлбөр 0 гэсэн бодит бизнесийн шаардлага тавьсан нь миний 7.5%-аас илүү утгатай санагдсан. /report ажиллаж байхад cart удаашрахгүй байх ёстой гэсэн санаа ч надад байгаагүй. AI санаа өгөхөд сайн ч тоог хэмжилтгүй таамагладаг тул шалгалгүй хуулж болохгүй юм байна.
